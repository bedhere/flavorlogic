一、这是什么

食之有理 FlavorLogic 是一个面向食饮研发的风味分析模拟器：把配方（原料 + 用量）换算成八维风味向量，算出「改成目标方案后每一维变了多少」，再按规则库给出可解释的补偿建议。

它做的事它不做的事
按用量加权算出八维风味的确切数值不替代感官评价小组的实测打分
给出每一维的绝对差值与变化比例不预测消费者喜好度、复购率或销量
按固定规则给出补偿方向、参考幅度与风险不判断配方是否安全、合规、可量产
把分析时的原料属性固化成快照存档不预测货架期、成本曲线与产线损耗

一句话：它负责把「凭感觉调」变成「有数据可推」，最终的确认仍然要回到打样与感官试验。中间那一行也是本项目在课设阶段的自我界定，写在这里是为了避免被误用。

二、八维风味向量：把配方变成一个可比较的坐标

八个维度固定为：甜、咸、酸、苦、鲜、辣、麻、脂香。每份配方最终都会得到一组八个数，这就是它的风味向量。

食材占比 = 该食材用量 ÷ 参与计算的用量合计（只计入具备风味属性的食材） 维度得分 = Σ（食材占比 × 该食材的该维度属性值） 偏移比例 =（目标得分 − 基准得分）÷ max(|基准得分|, 1) × 100%

三个要点值得注意：

  • 是加权平均，不是简单相加：所以把整份配方等比放大 2 倍，八维得分不变，改的只是总量。
  • 缺属性的食材不进分子也不进分母：它不会被当成 0 拉低得分，但会降低「数据完整度」，进而拉低置信度——这是刻意的设计，缺数据要看得见，而不是被悄悄抹平。
  • 除数有下限：比例计算时分母最小取 1，避免基准为 0 时出现除零或无穷大。

三、原料属性与数据来源：先把数据说清楚

八维属性存在原料档案里（ingredient 表的 sweet / salty / sour / bitter / umami / spicy / numbing / fat_aroma 八个字段），每条记录都带一个来源字段。当前演示库中 18 种原料的来源统一标注为：

课设演示相对评分

这句话的含义要说透：这些数值是用于演示计算链路与界面交互的相对评分，量纲是 0–100 的相对强度（例如白砂糖甜度 100、味精鲜度 100、食盐咸度 100），不是感官实验室测出来的绝对强度，也没有引用具体的检测报告。所以在正式研发场景里，正确的用法是：

  • 把原料属性替换成本企业自己的感官评价数据或供应商规格数据；
  • 属性值可以在管理后台直接维护（原料管理 → 编辑），改完之后新发起的分析会自动使用新值；
  • 已经完成的历史分析不会跟着变——原因见第十一节「结果快照」。
我们不把演示数据包装成实测数据。任何声称“基于实测原料数据库”的表述，在没有检测报告支撑时都是不成立的。

四、味觉打分与风味特征：先看清改完是什么味型

结果页的第一块面板是目标方案自身的八维得分，不涉及与基准的对比，回答的是「这份配方现在是什么味道画像」。

元素含义口径
单维得分该维度的加权平均得分0–100 相对量表，保留一位小数
平均强度八维得分的算术平均反映整体“存在感”，合计 ÷ 8
八维合计八维得分之和上限 800
风味特征得分最高的前三个维度得分为 0 的维度不列入

需要强调：这里没有「好吃 / 不好吃」的评级。得分高低只代表该维度在配方中的强度高低，不代表好坏——甜度高对一款甜品是目标，对一款控糖饮品就是问题。判断好坏要结合分析目标（控脂 / 减糖 / 区域适配）与人的感官结论。

五、八维雷达图：看轮廓，也看两条线的间距

雷达图把八个维度摊在同一个圆周上，适合看「味型轮廓」——哪几维突出、哪几维几乎贴地。结果页提供两种模式：

  • 单方案模式（默认）：只画目标方案，用于快速确认味型长什么样，画面干净、不受基准干扰。
  • 对比模式：把基准方案以虚线叠加，两条线之间的间距就是该维度的变化幅度，适合向他人解释“我们改了什么”。

六、绝对差值条形图：以 0 为中线，看真实变化量

雷达图有个天然弱点：刻度从 0 开始时，1.2 和 3.7 这种差异在图上几乎看不出来；而只看百分比又会掉进另一个坑。所以结果页额外提供一张以 0 为中线、向两侧生长的差值图。

绝对差值 = 目标得分 − 基准得分 变化比例 = 绝对差值 ÷ max(|基准得分|, 1) × 100% 状态判定：|变化比例| < 5% → 稳定；≥ 5% 且为负 → 下降；≥ 5% 且为正 → 上升
阈值常量取值作用
STABLE_THRESHOLD5%变化比例落在 ±5% 内视为「稳定」，不计入主要变化
MIN_BASELINE1比例计算的分母下限，避免基准趋近 0 时结果爆炸
LOW_BASELINE5基准得分低于 5 时，界面标注「基准极低 · 看差值」，不再强调百分比
MIN_ABS_DIFF1摘要里「主要变化」只收录绝对差值 ≥ 1 的维度，过滤 0.15 这类噪声

这四个常量共同回答一个常见疑问：为什么「加了 20g 白砂糖」会显示 +593% 这种吓人的数字？因为基准那份配方本来就几乎不甜（甜度基准极低），分母很小，比例自然被放大——但它真正的含义只是「从几乎不甜变成有点甜」。这类维度看绝对差值才有意义，界面也会主动提示。

七、真实案例：跟着演示库里的「减糖 100%」读一遍

下面全部数据取自本项目演示库中已保存的分析任务「减糖 100%：代糖复配与后味风险」（任务 5，历史结果，可直接在「分析历史」中打开原页面核对）。

目标方案把配方里的白砂糖完全替换为赤藓糖醇，共 5 项配料。结果摘要的原文是：

本次分析对比「0 糖茶饮基底」与目标方案，共 5 项配料；主要变化：苦 上升 202.44%、甜 下降 39.78%、酸 上升 30.61% 等 4 个维度。命中 1 条规则，给出 1 条参考建议。

逐维数值如下（保留两位小数）：

维度基准目标绝对差值变化比例状态该怎么读
甜77.3546.58−30.77−39.78%下降基准高、差值大，比例可信：甜度确实掉了一个量级

  • 比例不能单独看：同样是「上升」，苦 +202.44% 的实际影响（+2.49）远小于甜的下降（−30.77）。
  • 系统会自己指出噪声：咸的 +15% 因为绝对差值不足 1，没有进入摘要的「主要变化」。
  • 解释能追到原料：苦的偏移说明写着「主要来自：『赤藓糖醇』贡献增加 165.00」，直接指到具体原料。

八、规则引擎与补偿建议：建议不是生成出来的，是匹配出来的

建议不来自语言模型，而来自规则表 flavor_rule：每条规则由「触发条件 JSON + 执行动作 JSON + 说明」三部分组成，系统对八维偏移逐条匹配，命中的规则才会输出建议。

condition_json：{"operator": "LTE", "dimension": "umami", "changePercent": -10} action_json ：{"actionType": "ADD", "candidates": ["酵母抽提物", "香菇粉"], "referencePercentMin": 0.05, "referencePercentMax": 0.30}

当前演示库启用 4 条规则，覆盖课设里的四类研发目标：

规则编码规则名称适用目标触发条件给出的动作
UMAMI_DROP_GENERAL鲜味明显下降补偿综合分析鲜味变化比例 ≤ −10%从高鲜味原料中给候选（酵母抽提物、香菇粉），参考添加幅度 0.05%–0.30%
FAT_AROMA_DROP_REDUCE_FAT控脂场景脂香下降提醒控脂改造脂香变化比例 ≤ −15%提示关注：优先低用量增香或工艺增香，不直接恢复原油脂用量
SPICY_OVER_TARGET辣度超过目标范围刺激度调整辣度变化比例 ≥ +15%建议降低香辛料类原料用量 5%–20% 并重新分析
SWEET_DROP_REDUCE_SUGAR减糖场景甜味平衡减糖改造甜味变化比例 ≤ −20%提示关注：代糖复配、酸甜平衡调整，并要求做后味复核

每条建议固定输出六个字段，便于逐条核对与追责：对象（哪一维、哪个原料）、动作类型（增加 / 减少 / 提示关注）、参考幅度、触发原因（引用规则说明，并带上本次的实际变化值）、风险提示、命中规则名。控脂规则特意使用 NOTICE 而不是 ADD：减脂场景下直接加回油脂是自相矛盾的建议，这类“看似合理其实有害”的推断由规则显式禁止。

规则可在管理后台维护（规则管理 → 新增 / 编辑 / 停用），优先级数字越小越先匹配；命中规则的去重数量还会进入置信度计算。

九、区域口味画像：按权重折算，而不是凭印象

选择区域画像后，八维向量会按该区域的权重逐维折算（全国基准全部为 1.000，等于不折算），并根据权重强弱生成「建议加强 / 建议减弱」的区域偏好建议。

权重判定阈值：≥ 1.10 视为该区域偏好更强，提示加强；≤ 0.90 视为偏好更弱，提示减弱；介于两者之间不生成区域建议，避免无意义的噪声提示。

这几组权重是课设演示画像，用于演示区域适配的计算链路，不是权威口味调研结论。投入使用前需要用目标城市的消费者测试数据重新校准——建议的「风险提示」字段里也写了同样这句话。

十、数据完整度与置信度：结论有多可靠，可以被算出来

两块内容：完整度衡量「有多少用量真的有属性数据」，置信度把完整度与规则命中情况合成一个总分，提醒你这条结论值不值得直接拿去试产。

数据完整度 = 具备风味属性的用量 ÷ 配方总用量 × 100% 结果置信度 = min(基准完整度, 目标完整度) × 0.8 + min(命中规则去重数 ÷ 3, 1) × 100 × 0.2 // 上限 100

用第七节那个真实案例代入，可以完整复现 86.67%：

  • 基准与目标的完整度都是 100%（5 项配料的属性数据齐全），取较小值 = 100；
  • 100 × 0.8 = 80.00；
  • 命中 1 条规则（减糖场景甜味平衡），去重后命中数为 1，min(1 ÷ 3, 1) = 0.3333，× 100 × 0.2 = 6.67；
  • 80.00 + 6.67 = 86.67%，与结果页显示一致。

怎么用这个数字：完整度掉下来（比如加了没有属性数据的复配原料）会同时拉低置信度，这是提示你“别把它当确定结论”。需要说明的是，权重 0.8 / 0.2 与「3 条规则算满覆盖」都是本项目自定的口径，目的是让可靠度可比较、可解释，它不是行业标准公式，也不能理解为“86.67% 的概率正确”。

十一、结果快照与可追溯：历史结论不会事后变形

每次分析都会把当时的基准配方与目标方案连同食材属性值一起固化成快照存档（analysis_result.baseline_json / target_json），并记录引擎版本号（当前 RULE-1.0）。这意味着：

  • 管理员后来调整了某个原料的属性值，不会改变历史分析里的数字；
  • 同一份配方在不同时间分析得到不同结果时，可以回到旧记录确认当时用的属性值；
  • 每条分析记录都能追溯到输入、输出、命中的规则与建议，导出或答辩时可以直接对着数据说明。
口径说明：快照保证的是「历史结论可复现」，不保证「结论长期正确」——原料属性本身被修正后，应当用新数据重新分析，而不是继续引用旧结果。

十二、边界与免责：哪些话我们不说

能力边界说明
不是感官实测所有得分来自「用量 × 原料相对属性」的加权计算，缺少真实感官评价小组的结果，不能替代品评。
不判定安全与合规不涉及食品添加剂限量、过敏原法规、微生物与保质期等合规判断。分析页的过敏原与成本字段只是研发备忘。
不预测市场不预测销量、复购与消费者偏好，区域画像只是计算权重，不是市场调研结论。
不替代工艺加热、发酵、乳化、干燥等工艺对风味的实际影响未建模，结果只针对配方组成。
比例有适用条件基准极低（< 5）时百分比会被放大，须以绝对差值为准；界面会主动标注。
数据决定上限原料属性越完整，结论越可用；属性缺失会通过完整度与置信度如实反映，不会被隐藏。

一句话总结本系统的定位：它把打样前的试错成本降下来，把判断依据摆到桌面上；最终确认仍然由人和感官试验完成。本项目为课程设计阶段成果，演示数据仅用于功能验证。

十三、常见问题

加了 20g 白砂糖，为什么显示 +593%？

因为基准配方的该维度得分极低（例如 1.58），比例的分母很小，算出来自然很大。这个数字对应的真实语义是「从几乎不甜变成有点甜」。基准低于 5 时，界面会标注「基准极低 · 看差值」，并按绝对差值表述，摘要里也不再写百分比。

为什么雷达图看起来“没变化”？

雷达图刻度从 0 开始，当某一维只变化 0.5–2 时，图形上几乎看不出来。这类差异请用绝对差值条形图（以 0 为中线）查看，它能直接显示每一维的正负与幅度。

「稳定」是怎么判定的？

变化比例的绝对值小于 5% 记为稳定，不进入「主要变化」摘要；此外摘要要求绝对差值不小于 1，避免 0.15 这类噪声被写成结论。

置信度为什么下降了？

完整度在公式里占 0.8 权重，且取基准与目标中较低的一个。只要新增了没有属性数据的原料，完整度就会下降，置信度随之下降——这是刻意设计的提醒，而不是计算错误。

建议可以直接执行吗？

建议给出的是方向、候选原料与参考幅度，属于打样前的参考。每条建议都带风险提示字段，例如代糖复配需要后味复核。请以实际打样与感官结论为准。

换成自己的原料数据要怎么做？

登录管理员账号后进入「原料管理」，逐条维护八维属性与数据来源；之后新发起的分析会使用新数据，历史分析结果保持不变（快照机制）。
