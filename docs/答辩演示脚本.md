# 食之有理 FlavorLogic 答辩演示脚本

> 目标：10 分钟内讲清「项目做什么 → 核心链路怎么跑 → 技术怎么实现 → 边界在哪里」
> 原则：**先讲配方分析主链路，再讲知识库与后台**，避免被误解为普通文章管理系统。

## 二、演示流程与话术

### 第 1 步：开场（30 秒）

> 「我的项目叫**食之有理 FlavorLogic**，是一个面向食品研发场景的配方与风味分析 Web 应用。
> 要解决的问题是：中小食品企业改配方基本靠师傅经验和反复试错，替换一个原料、减糖 30%、换个区域卖，
> 到底风味会怎么变、需要补什么，**没有量化依据**。
> 我的做法是把配方结构化成八维风味向量，算出调整前后的偏移，再用规则库给出可解释的补偿建议。」

### 第 2 步：首页（1 分钟）

打开 `/`（**未登录状态**），指出三点：

1. 「首页对游客开放，展示项目定位与最新的研发知识文章」；
2. 「三个指标对应产品能力：八维风味向量、从 3 次试错压缩到 1 次有依据的试产、以及知识文章数量」；
3. **把鼠标移到顶部导航「产品能力 / 怎么看结果」上**，面板会展开：
   左边是按主题分组的说明条目，右边是一张推荐卡片 ——
   话术：「首页不只是宣传页：**任何一个数字，都能从导航点进去看到它怎么算出来的**」。
   点其中任意一条（例如「绝对差值条形图」）会跳到说明页的对应章节，**游客无需登录**；
4. 首页下半部分的「**可信度与口径**」三张卡片，分别对应数据来源、判定阈值、置信度算法；
   话术：「这三件事是评审最容易追问的地方，我直接把它们写在首页上」；
5. 点击右上角「开始使用」→ 强调注册后默认为普通用户，管理员权限由后台分配；
   注册成功后**回到登录页**（用户名已自动填好），需要手动输入密码登录 ——
   可顺带说明「注册只创建账号、不建立会话」这一安全考虑。

> 备用：如果评委追问「+593% 这种数是不是算错了」，直接打开
> `features.html#example`（导航「怎么看结果 → 一个真实案例」），
> 那里用演示库任务 5 的真实数据逐维解释了「比例什么时候可信、什么时候要看绝对差值」。

### 第 3 步：登录与权限（45 秒）

- 用 `demo / Demo@123` 登录 → 「这是普通用户的视角：工作台、配方库、分析历史、个人中心」；
- 直接访问 `/admin/users.html` → 被拦截并跳转 403 页面，说明**页面级和管理员接口级双重拦截**；
- （可选）用 `admin / Admin@123` 登录，指出侧栏多出「系统管理」分组。

### 第 4 步：工作台（30 秒）

> 「工作台汇总了配方数、分析任务数、最近分析时间，以及最近的配方和分析记录，
> 所有入口都能跳转到对应专业页面，工作台本身不做编辑。」

### 第 5 步：核心链路 —— 配方录入与发起分析（3 分钟）

进入 `配方库 → 香辣牛肉干（改版前）→ 发起分析`（编辑配料与发起分析是两个独立入口，演示时先说明这个分工）：

1. 指出**基准配方**：7 项配料，每行显示该食材的八维属性摘要（「这就是可计算性的来源」）；
2. 下方**发起风味分析**面板：分析类型选「原料替换」，说明「成本上涨，想把主料牛肉换成鸡胸肉」；
3. 目标方案里把牛肉改为鸡胸肉，其余不动 → 点击「提交分析」；
4. 等待 1 秒跳转结果页，逐步讲解：
   - **摘要**：「脂香下降 60%，苦味下降 39%，鲜味下降 32%」；
   - **雷达图**：绿色是基准、蓝色是目标，「一眼看出塌在哪一维」；
   - **偏移明细表**：绝对差值 + 变化比例 + 状态（稳定 / 下降 / 超出建议范围），并给出**主要影响因素**「牛肉贡献减少、鸡胸肉贡献增加」；
   - **补偿建议**：命中规则「鲜味明显下降补偿」，给出候选食材（酵母抽提物、香菇粉）与参考幅度 0.05%-0.30%，并带**触发原因**；
   - **快照对比**：左基准、右目标，「这里固化的是分析当时的食材属性」；
   - **解释与免责**：计算口径、数据完整度与置信度公式、以及「不等同于实验室检测」的声明。

> 讲解要点：**每一条建议都能回答「为什么」**，这是和「让大模型随便给个建议」的本质区别。

### 第 6 步：分析历史与试产反馈（1 分钟）

进入「分析历史」：

- 展示 4 条演示记录，分别命中不同规则：控脂（脂香 -20.4%）、减糖（甜味平衡）、原料替换（鲜味补偿）、区域适配（西南麻辣微调）；
- 打开「控脂 25%」任务，指出**区域/约束**「过敏原：花生」——说明命中过敏原的候选食材会被自动剔除；
- 在结果页底部提交试产反馈（有帮助 / 评分 / 试产结果 / 文字），说明这是为第二阶段「反馈 → 规则校准」预留的数据闭环。

### 第 7 步：研发知识库（45 秒）

- 列表页支持分类 + 关键词 + 分页；详情页展示来源、发布时间与相关文章；
- 强调「知识库是**支撑模块**，不是项目主功能」；正文经过服务端白名单过滤，防止 XSS。

### 第 8 步：后台管理（1.5 分钟）

用 `admin` 登录，依次展示：

1. **食材与规则**：八维属性可维护（0-100 校验、名称唯一）、停用不删除，「规则面板展示 condition/action JSON 原文，可以解释每条建议是怎么来的」；
2. **文章管理**：新增/编辑/发布/下架 + 点击「模拟同步」演示**去重**：来源地址重复、正文指纹重复会直接拦截，标题相似只提示人工确认；
3. **用户管理**：启用禁用、角色调整（并演示「不能禁用自己」的保护）；
4. **分析任务**：全平台任务查看，管理员**只能看不能改**；
5. 回到工作台底部看**操作日志**（谁在什么时间改了什么）。

### 第 9 步：收尾（30 秒）

> 「技术上：后端是 Java Servlet + 原生 JDBC 的 Model-DAO-Service-Servlet 四层结构，没有使用任何框架；
> 数据库 15 张表，包含任务快照、试产反馈、配料调配知识库与目标模板；前端按设计规范复刻，全部静态资源本地化，断网也能跑。
> 需要强调的是**边界**：风味数值是课设演示用的相对评分，结果用于打样前的方向性参考，
> 不能替代感官评价和食品安全审核——这也是我在结果页显式声明免责的原因。」

## 三、常见提问与应答

**Q1：你的项目创新点是什么？**
> ① 从「文本建议」转向**参数化推演**：先把配方结构化成八维向量再计算，结果可比较、可保存、可复查；
> ② **可解释**：每条建议都有触发规则、参考幅度、风险提示和主要影响原料；
> ③ **快照沉淀**：分析时固化食材属性，历史结果不会因为基础数据后来调整而失真；
> ④ 面向**研发约束**（替换/控糖/控脂/刺激度/区域）而不是菜谱推荐。

**Q2：八维风味的数据从哪来？可信吗？**
> 课设阶段是**演示用相对评分**，来源标注为「课设演示相对评分」，用于验证业务与技术闭环；
> 计设阶段计划接入文献与国标感官方法、做多人标注一致性检验（Cohen's kappa）并标注来源。
> 我**不声称**它等同于实验室检测结果，这一点在结果页和数据表注释里都写明了。

**Q3：你用了大模型吗？为什么不让它直接给配方？**
> 用了，但**只让它做解释和检索，不让它做决策**——决策仍然是规则引擎加结构化知识库完成的。
> 原因很直接：通用大模型输出「脂香下降 18%、补 0.2% 酵母抽提物」这类参数**不可复现、不可溯源**，
> 同一个问题问两次可能给出不同数字，这样的结果进不了真实的研发流程。
> 所以我把它限定在三个位置：把引擎结果翻译成人话、基于调配知识卡做带引用的问答、
> 把「油脂降 25%」这类自然语言转成结构化草案——而**草案还要回落规则引擎重算、由用户确认后才入库**。
> 每次调用都写 `ai_call_log`，记录这次引用了哪几张知识卡、耗时多少、有没有走降级；
> 而 `ai.enabled=false` 时系统会退回引擎原有的解释文本，**断网也能完整演示**。
> 一句话：AI 是交互层和解释层，可解释的决策链路没有被削弱。

**Q4：配料调配知识库为什么不做成文章，而要做成知识卡？**
> 因为研发要解决的不是「读一篇文章」，而是「鲜味缺了补什么、补多少」。
> 文章是长文本，检索出来还得人自己读完再提炼，程序没法直接消费。
> 知识卡把它拆成结构化字段——目标维度、触发场景、候选配料、用量区间、起效原理、风险、过敏原、依据来源——
> 规则引擎能直接用它生成建议（从「建议加强鲜味」升级为「补 0.05% 到 0.30% 酵母抽提物，
> 依据是呈味核苷酸与谷氨酸协同，风险是过量呈酵母味」），AI 问答也能引用它并**说出依据了哪几张卡**。
> 目前库里是 64 张知识卡加 22 条配料搭配关系，覆盖八维风味与六种研发目标。

**Q5：如果食材没有属性数据怎么办？**
> 该食材**不参与加权计算**（既不进分子也不进分母），同时会降低「数据完整度」，进而降低结果置信度；
> 结果页会列出「以下配料缺少风味属性数据」，并在配方库标记「有食材缺属性」提示管理员补充。

**Q6：如何防止越权访问别人的配方和分析记录？**
> 三层：`AuthFilter` 拦截未登录、`AdminFilter` 拦截后台；Service 层每次读写都校验 `user_id` 归属，
> 越权直接返回 403；DAO 层所有查询都带用户条件，不依赖前端传参。

**Q7：数据库设计了哪些表？为什么有快照表？**
> 15 张表：用户、文章分类与文章、食材、区域画像、风味规则、配方与配方明细、分析任务、分析结果、分析反馈，
> 以及配料调配知识库的三张表——调配知识卡 `flavor_knowledge`、配料搭配关系 `ingredient_pairing`、AI 调用日志 `ai_call_log`，
> 最后是目标模板表 `goal_target`——它把「研发目标」展开成八维目标向量，是配方生成器的输入契约；**50 条规则全部写在数据里，新增研发目标不用改 Java**。
> 知识卡的设计要点是：把「缺什么味补什么料」的经验拆成结构化条目（维度、场景、候选配料、用量区间、原理、风险），
> 而不是堆成一篇文章——这样规则引擎能直接消费它，AI 问答也能引用它并给出可追溯的来源。
> `analysis_task` 里存了基准/目标快照 JSON，`analysis_result` 存结果 JSON——
> **快照是为了可复现**：研发要能回看「当时为什么这么判断」，而不是只看到被后续修改覆盖的数据。

**Q8：为什么 MySQL 5.7 下 CHECK 约束不生效？**
> 5.7 只解析不执行 CHECK（8.0.16+ 才强制），所以字段合法性我放在 Service 层做（八维 0-100、状态枚举、
> 评分为 1-5 等），数据库约束作为 8.0 环境下的额外保障。这一点我在 README 里主动说明了。

**Q9：如果两个人同时提交同一份分析会不会出问题？**
> 不会：任务先落 `PENDING` 再执行，每次分析都是独立任务与独立结果行（`analysis_result.task_id` 唯一），
> 反馈表用 `(task_id, user_id)` 唯一键做 upsert，重复提交是更新而非新增。

**Q10：前端为什么不用 Vue / React？**
> 课程要求使用 HTML/CSS/jQuery/Bootstrap；而且这个项目的交互集中在表单、表格与图表，
> jQuery + 统一的 `common.js` 公共层（API 客户端、应用外壳、组件库）已经足够，也更容易在答辩时讲清每一行代码。

**Q11：这个项目下一步做什么？**
> 近期：把调配知识卡接入规则引擎，让建议直接带出候选配料与用量区间；再补上 AI 解读与知识库问答两个入口。
> 计设阶段：扩充食材属性数据（2000+）、完善区域口味画像、增加多方案对比与约束优化、找 1-2 家企业试跑并输出指标；
> 毕设阶段：研究风味预测模型、区域偏好适配与反馈学习，做离线评估与消融实验。

## 四、故障应急

| 现象 | 处理 |
|---|---|
| 页面打不开 | `stop-flavorlogic.ps1` 后重新 `start-flavorlogic.ps1`；查看 `tomcat-runtime/logs/catalina.*.log` |
| 数据被改乱 | `mysql -u root -p flavor_logic < database/demo_data.sql` 恢复演示数据（先清空对应表） |
| 分析报「没有可用于计算的食材属性数据」 | 后台「食材与规则」确认食材为启用状态且八维有值 |
| AI 解读报错 / 迟迟不返回 | 检查 `src/main/resources/ai.properties` 的 `enabled`、密钥与 `timeout`；演示现场最稳妥的做法是把 `ai.enabled` 改为 `false`，系统回落引擎原有解释文本，流程不受影响 |
| 登录失败 / 账号被禁用 | 用管理员账号在后台「用户管理」重新启用，或重新执行演示数据脚本 |
| 端口被占用 | 修改 `tomcat-runtime/conf/server.xml` 的 Connector port，或关闭占用 8080 的程序 |
