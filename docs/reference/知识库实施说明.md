# 食之有理：外部资料知识库实施说明

## 1. 当前阶段的边界

本阶段已经把“资料进入系统后如何留痕、审核、检索”落到 MySQL 和 Java 后端，暂不抓取外部网站，也不部署或连接 Yuxi。

原因是网页内容不能直接等同于正式知识。必须先记录来源、许可、抓取时间和正文指纹，再由管理员确认原文是否可靠、结论是否能支撑项目规则。只有 `APPROVED` 的来源文档可被检索；只有审核后的证据声明才能进入食材属性、规则或建议。

当前链路如下：

```text
来源站点白名单
      ↓
抓取任务 / 人工导入
      ↓
source_document（REVIEW_PENDING）
      ↓ 人工审核
APPROVED ──→ MySQL FULLTEXT 检索 ──→ 分析说明 / 证据引用
      ↓
evidence_claim ──→ ingredient_attribute_version / rule_evidence
      ↓
规则引擎和配方建议
```

## 2. 数据怎么存

### 2.1 原始层：`source_site`、`crawl_job`、`source_document`

- `source_site`：站点名称、根地址、robots/条款地址、许可类型、是否允许自动获取、请求间隔。
- `crawl_job`：一次抓取任务的状态和成功/失败数量，便于重试和审计。
- `source_document`：清洗后的纯文本或 Markdown、原文 URL、标题、摘要、发布时间、获取时间、正文 SHA-256、审核状态和可选文件路径。
- 文件较大时，原始 HTML/PDF 放在应用配置的文件目录，MySQL 保存路径、摘要和指纹；不要把二进制大文件塞进数据库。

`PRODUCT_LABEL` 类型的证据声明只表示某个条码产品的包装或数据库标签值，不能直接转换为通用食材的八维风味评分。

`source_document` 的 `url` 和 `content_hash` 都唯一，避免重复导入。中文检索使用 MySQL 5.7 的 `FULLTEXT ... WITH PARSER ngram`，当前规模不需要先部署独立搜索服务。

### 2.2 证据层：`evidence_claim`

一篇网页不能直接成为一条风味属性。人工审核时把它拆成可引用的声明，例如：

```json
{
  "documentId": 101,
  "ingredientId": 12,
  "dimension": "sweet",
  "claimType": "MEASUREMENT",
  "claimText": "样品在指定条件下的相对甜度为 65",
  "quoteText": "原文中能够支撑该结论的短摘录",
  "amountMin": 0.1,
  "amountMax": 0.3,
  "amountUnit": "%",
  "method": "感官评价 / 仪器检测",
  "evidenceLevel": "LITERATURE",
  "reviewStatus": "REVIEW_PENDING"
}
```

`quote_text` 保留短摘录，`claim_text` 写成项目可以使用的结构化结论；两者都要能回指原文 URL。没有明确测试条件、单位或适用范围的内容只能做背景检索，不能直接改写正式属性。

### 2.3 数值层：`ingredient_attribute_version`

每次修改食材八维属性都新增版本，不覆盖旧值。版本记录保存口径、浓度、温度、测量方法、不确定性、来源文档和审核人。规则引擎只读取审核通过且当前生效的版本；分析历史仍使用已有快照。

### 2.4 规则层：`rule_evidence`

规则或知识卡可以关联一条或多条证据声明。这样建议页面可以展示“为什么给出这条建议、依据哪篇原文、适用条件是什么”，而不是把网页内容直接当作不可解释的模型输入。

## 3. 先接哪些数据源

第一批建议选择有 API、下载文件或明确许可的数据源，不要从搜索结果页、论坛、营销软文批量复制：

1. **USDA FoodData Central**：营养和食品成分数据，提供 API 与数据集下载，适合补充标准化食品成分字段；需要把营养字段和本项目“八维风味评分”分开，不能直接混算。
2. **FAO/INFOODS**：食品成分数据标准和数据库入口，适合做字段口径、单位和来源说明的参考。
3. **Open Food Facts**：包装食品条码和配料信息，适合作为补充来源；数据为用户贡献，必须保留许可和低置信度标记，不能直接覆盖权威值。
4. **论文、标准和机构公开页面**：先人工导入 PDF/HTML 的关键段落，审核后形成 `evidence_claim`。涉及法规或标准时只保存允许使用的必要摘录和链接。

建议暂不把“各大网站”定义成无限抓取范围。现在已经有来源站点白名单接口和单 URL 采集任务：先为每个站点建立 `source_site` 记录，确认 robots、服务条款、许可和访问频率后，再把 `crawlAllowed` 改为 `1`。采集任务不会递归跟踪链接，每次最多获取一个文本 URL，结果仍进入人工审核队列；没有明确授权的站点继续使用人工导入入口。

## 4. 导入、审核和使用方式

### 4.1 现有接口

- `POST /api/admin/knowledge/documents`：管理员导入清洗后的标题、URL、摘要和正文，自动计算指纹，状态固定为 `REVIEW_PENDING`。
- `GET /api/admin/knowledge/documents`：后台分页查看待审核、已通过、已拒绝或已归档文档。
- `PUT /api/admin/knowledge/documents/{id}`：管理员写入审核状态和审核意见。
- `/api/admin/knowledge/sites` 与 `/api/admin/knowledge/jobs`：登记站点白名单、创建单 URL 任务并查看任务结果。
- `GET /api/knowledge/search?q=甜味&limit=10`：登录用户检索已审核文档；当前响应会标明 `provider = MYSQL_FULLTEXT`。
- `POST /api/admin/knowledge/claims`、`PUT /api/admin/knowledge/claims/{id}`：录入并审核证据声明。
- `POST /api/admin/knowledge/attributes`、`PUT /api/admin/knowledge/attributes/{id}`：录入并审核食材属性版本；`PUT .../{id}/apply` 才会显式写入 `ingredient` 主表。
- `/api/admin/knowledge/evidence-links`：把已批准声明关联到风味规则或调配知识卡。

导入接口只接收已经清洗过的文本，不在 Servlet 中访问外网。后续增加抓取器时，抓取器仍然先写入审核队列，再由同一套审核接口处理。

### 4.2 人工审核清单

1. URL 是否属于登记过的站点，是否符合许可和使用范围。
2. 原文是否能打开，发布时间、作者/机构和版本是否记录完整。
3. 结论是否包含单位、样品条件、浓度、温度和适用范围。
4. 是否把“营养指标、营销描述、个人经验”误当成风味强度。
5. 是否能摘出短引文并写出一条可验证的 `claim_text`。
6. 确认后才允许进入 `evidence_claim` 和属性版本；不确定的内容保留为背景资料或拒绝。

## 5. Yuxi 何时接入

Yuxi 只承担文档解析、切分、向量/关键词检索和问答上下文召回；MySQL 继续保存业务状态、审核状态、证据声明和规则输入。Yuxi 返回的文档 ID、文件 ID、索引状态写回 `source_document.yuxi_*`，便于追踪和重建。

接入时新增 `YuxiKnowledgeProvider implements KnowledgeProvider`，通过配置切换：

```text
MYSQL_FULLTEXT  →  本地开发、审核后台、无 Yuxi 环境
YUXI            →  已审核文档的语义检索和问答召回
```

导入顺序应为“审核通过 → 上传/解析 → 确认索引完成 → 允许问答引用”。Yuxi 官方文档说明其知识库上传、解析、切分、索引是异步流程，因此不能只记录上传成功就把文档当成可检索。到这个部署节点时，需要先确定 Yuxi 版本、存储/向量组件、网络地址和凭据，再单独做联调。

## 6. 更轻量的替代方案

按当前课设的规模，建议顺序是：

| 方案 | 用途 | 当前建议 |
|---|---|---|
| MySQL FULLTEXT ngram | 中文关键词、来源和审核状态 | **现在就用**，零新增服务 |
| Qdrant Local | 需要语义检索但不想部署完整 Yuxi | 后续小型实验可选，Docker 本地运行 |
| Chroma PersistentClient | Python 原型或离线小数据集 | 适合独立实验，不直接嵌入本 Java 主流程 |
| Milvus Lite | 需要接近 Milvus 的本地向量实验 | 更适合 Python 试验，不建议先加入本课设 |
| Yuxi | 文档解析、知识库编排、问答 | 等审核数据稳定后再接 |

因此当前不建议为了“看起来像 AI”立刻增加向量数据库。先把来源和证据做成可审计数据，达到几十到几千篇文档后，再用同一 `KnowledgeProvider` 接 Qdrant 或 Yuxi，迁移成本较低。

## 7. 下一阶段实施顺序

1. 用本地 MySQL 执行最新 `database/flavor_logic.sql`，确认新表建立。
2. 创建少量人工审核样本，不连接外网，验证导入、去重、审核、检索和权限。
3. 选定 2～3 个允许使用的数据源，通过来源站点白名单接口登记到 `source_site`，明确字段映射和证据等级。
4. 在白名单基础上继续增加限速调度、重试策略和 API 专用字段映射；现有单 URL 任务已经包含域名、robots、文本类型、大小、重定向和内网地址检查。自动采集还需要部署环境显式设置 `FLAVORLOGIC_CRAWL_ENABLED=true`，抓取结果只进 `REVIEW_PENDING`。
5. 把已审核文档拆成 `evidence_claim`，再创建 `ingredient_attribute_version`；审核通过和应用到 `ingredient` 主表是两个独立动作。
6. 增加证据声明和属性版本的后台录入/审核页面，并让规则引擎只读取 `APPROVED` 数据。
7. 做检索质量和建议正确性评估，确认 MySQL 检索不足后，再讨论 Qdrant 或 Yuxi 部署。
