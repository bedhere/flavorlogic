## 下一步：先完成知识库闭环验收

目标是跑通“来源文档 → 审核 → 证据声明 → 属性版本 → 应用到主表 → 配方分析 → 结果引用”，形成可重复演示的真实案例。

1. 核对实际 MySQL 表结构与正本 SQL。旧库先备份，按需执行 `database/upgrade_knowledge_tables.sql`；核对已有证据声明类型是否支持 `PRODUCT_LABEL`，避免仅建表而未完成旧表结构升级。
2. 先用少量人工导入资料验证去重、审核与权限，再逐步达到 10–20 个来源文档、20–50 条证据声明、5–10 种核心食材的规模。
3. 至少完成一条具有明确测量口径的风味属性版本链路。Open Food Facts 的糖、脂肪、盐标签值只能代表具体产品，不能直接换算为通用食材八维评分。
4. 验证未审核内容不能进入检索或结果引用；属性通过审核后仍需显式应用；修改属性后历史分析保持原快照，新分析展示新版本和来源。
5. 留下验收记录：案例输入、关键接口结果、页面截图、预期与实际结果，以及数据库升级步骤。

完成标准：普通用户可查到已批准资料，管理员可完成证据与属性审核，一次新分析能展示对应来源，历史结果不被后续属性修改覆盖。

## 然后的开发顺序

1. **冻结分析结果契约 V1。** 把配方、工艺预留字段、八维结果、建议、引用和引擎版本整理为稳定结构，为模型和 AI 共用。
2. **先做分析结果页 AI 解读。** 只解释引擎既有结果，保留知识卡/来源引用；无依据时明确说明，关闭 AI、缺密钥或调用失败时回落本地文本。完成后再扩展知识库问答、自然语言草案与首页意图解析。
3. **启动感官数据采集。** 从甜酸、甜苦等交互设计盲样、评分表和实验记录；先验证小批数据质量，再扩大标注规模，这是提高预测能力的关键前提。
4. **用真实数据拟合并评估非线性模型。** 与当前线性基线比较，验证交互方向和误差改善，再接入 Java 推理与结果页误差带。
5. **用同一批查询比较检索策略。** 根据 Recall@5、MRR 和口语查询效果决定是否接入向量召回或 Yuxi。
